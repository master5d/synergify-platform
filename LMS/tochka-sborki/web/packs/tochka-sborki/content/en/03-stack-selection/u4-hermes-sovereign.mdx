<Phase type="activation">

Think of a moment when one tool tried to do everything at once — and broke down halfway through.

Don't picture it as a "context window problem." Picture it as **your own vegetable garden versus the market** 🌱: the gardener planted it, watered it, harvested it — and knows every plant. The market buyer gets ready produce fast, no fuss. Hermes is the gardener who **keeps the plan at home** and sends workers out for specific results. It doesn't trust the whole harvest to a single stall.

Notice in your head: which part of your AI workflow suffers most because the agent **does everything in sequence** and loses the thread mid-task?

</Phase>

<Phase type="reflection">

Picture a theatre director 🎭 at rehearsal. They don't play every part in turn. They hold **the whole production in their head** and give each actor exactly enough to play their scene. The actors don't need to know the ending — the director does.

Catch that same logic here:

> "I asked Claude Code to refactor the auth module. By the 5th file it started applying the backend style to the frontend, forgot my original plan, and burned 200K tokens to recover."

That's **context-saturation**: the actor tried to play every role. Hermes holds **only the plan and state** — the director's role:
1. Frames the subtask
2. Launches a sub-agent (Aider in a worktree, or Claude Code) — "actor enters the scene"
3. Receives the result, verifies
4. Updates the plan, next entrance

Hermes's context isn't eaten by implementation. Worker contexts are atomic and tightly scoped.

</Phase>

## How the author's setup works: an owner-controlled stack on personal hardware

Here **Sovereign** means your own stack: models on your hardware, data stays away from providers, and the fallback chain remains under your control. This is not a product description; it is the general design principle.

```text
Author's programs: Claude Code, Codex, and Hermes
                         │
                         ▼
One model gateway: LiteLLM on an always-on Mac mini
  • programs use one endpoint through pool aliases
    (a pool = interchangeable models under one name)
  • provider keys live only on this machine
  • free provider tiers first; the local step comes last
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
Ordinary tasks: cloud pools     Personal and medical data:
with fallback choices           a separate pool with no cloud neighbors
             │                       │
             └───────────┬───────────┘
                         ▼
Local model on a 128 GB Mac Studio
(an open model running locally)

The separate Linux machine is the console: gateway and monitoring panel.
Hermes lives on a separate machine running Linux.
```

Real route example: **Claude Code → LiteLLM → Cerebras gpt-oss-120b**. **Hermes → LiteLLM with a fallback chain** follows the same principle: Hermes dispatches work to executors (Claude Code, Codex), while the shared gateway selects models.

## What to install in practice

The official Hermes repository is [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent). The official LiteLLM repository is [BerriAI/litellm](https://github.com/BerriAI/litellm). Install Hermes and configure the gateway by following their READMEs; the course has no public repository of its own, so this lesson does not provide invented install commands.

A complete stack like this takes weeks, not an evening: several machines, a gateway, model pools, monitoring, fallback routes, and rules for sensitive data. The course gives you the minimum experience: local LiteLLM on `localhost:4000` (u3) + one local model through `llama-server` as the final step + Hermes on top, following the official instructions.
