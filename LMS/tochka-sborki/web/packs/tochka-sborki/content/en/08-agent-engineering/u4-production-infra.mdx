<Phase type="activation">

A prototype agent that runs on your laptop is **20% of the work**.

Don't picture this as "code you still need to write" — picture it as **the city's grid under the asphalt**. The substation, the cables, the mains, the valves. A passerby sees only the sidewalk. But the lights in your apartment stay on because the invisible infrastructure beneath is doing its job. And it's precisely what keeps them from going dark while you sleep.

Run it in your head: what in your agent keeps the lights on when you're not around? And what's the first thing that trips when the voltage dips?

</Phase>

<Phase type="reflection">

Production infrastructure for agent systems has 6 building blocks:

1. **Execution** — where and how it runs
2. **Observability** — how you see what's happening
3. **Reliability** — what to do when things break
4. **Cost control** — how not to go broke
5. **Security** — who has access
6. **Quality** — how you know the agent answers well

The vibe coder usually thinks only about (1). The agent engineer thinks about all six.

Don't picture this as "a list of settings" — picture it as a **hydroelectric dam**. All you see is the wall. But the real work lives in the floodgates, the water-level sensors, the emergency spillways nobody notices until a flood comes. Those are what keep the city dry.

Each of the six blocks is one such gate. While everything is calm — it's invisible. What happens when the first gate on your agent fails?

</Phase>

<Phase type="concept">

**My production stack for agent pipelines**

Configuration:
- **Server:** one rented Hetzner machine (currently CX33, roughly €10–12/mo). It is the only machine with Docker: containers host the mail agent, mailing service, search, proxy for worker agents, and Postgres.
- **Network edge:** only services that must be public are published; everything else listens on `127.0.0.1` or is reachable over a private network between my devices (Tailscale). Cloudflare is used for external access.
- **Control desk:** an always-on Mac mini M4 runs the model gateway and the monitoring dashboard.
- **Local inference:** a 128 GB Mac Studio is the last step in the chain when free cloud pools have refused or exhausted their quotas, and the only step for personal and medical data: by design, that data never goes to the cloud.
- **Model gateway:** every script calls models through LiteLLM, using pool aliases (a group of interchangeable models under one name). Provider keys live only on the gateway machine; they are not in project code.

**Rakes that cost me days of debugging** (save these, no need to step on them yourself):

**Rake 1: a Docker port on `0.0.0.0` bypasses the firewall**
> The first server self-scan on October 1, 2026 found the no-code orchestrator's (n8n) web interface exposed directly to the internet: Docker published `0.0.0.0:5678` outside the host firewall. The orchestrator was removed entirely.
> **Rule:** a server service listens on `127.0.0.1` or a private network; public access goes only through Cloudflare.

**Rake 2: a green container is not a live pipeline**
> The mail agent lost Gmail access (`token refresh failed`). The container kept running, but messages were no longer processed.
> **Rule:** watch the “hours since the last email,” not just the container status.

**Rake 3: a service without a gateway key silently found nothing**
> The log accumulated 684,837 refusals until a missing key was made fatal at startup.
> **Rule:** a missing gateway key must stop the service immediately, rather than becoming an empty result.

**Rake 4: there is no per-run limit**
> A stuck queue turned every tick into hundreds of calls.
> **Rule:** 3 retries inside a pass, 5 passes before the dead-letter queue.

All pipelines are code in git. OS timers run them: launchd on Macs, systemd timers on Linux, and Task Scheduler on Windows. Each pipeline records who is notified when it breaks.

This stack used to include a no-code orchestrator and separate tracing; both were removed in late September 2026: the first because it was exposed to the internet and had no working workflows, the second because nobody read its data. The choice of tools is yours; this lesson describes what actually works for the author.

**LLM fallback chain**

Free cloud pools go first; their quotas add up. Local inference is the last step. The concrete example is two aliases, `fast-pool` → `local-floor`:

```yaml
fallbacks: [fast-pool, local-floor]  # scheme, not a LiteLLM config
```

Project code contains neither provider names nor provider keys: it calls pool aliases through the single model gateway. If the free pool refuses a request or runs out of quota, the request goes to the local step.

When the first provider goes down — the next one catches the call. This is **reliability** at the infra layer, not the prompt layer.

**Observability through the M4 dashboard:**

The “Usage” tab shows spend and calls across all pools from the gateway's own log, SQLite `usage.db`. There is no separate tracer: this stack relies on aggregate calls and costs, not per-step tracing. What the model answered on a specific call is visible in the service's own log; for the Gmail agent, that is the draft text and the label reason on the dashboard.

<Phase type="practice">

For your workflow from unit 3, answer:

**Execution:**
- Where does it run? (your laptop? an OS timer? an event trigger?)
- What if the run lands at a moment when the machine is off?

**Observability:**
- If step 4 failed 3 days ago — how do you find out?
- How do you see what the LLM actually replied?

**Reliability:**
- What to do if the LLM provider returned a 500?
- What if input arrived in an unexpected format (broken JSON, emoji in filename)?

**Cost:**
- How many LLM calls per day in the worst case?
- What happens if the bill starts multiplying (e.g., a retry loop)?

**Security:**
- Where are the API keys stored?
- What would another person see if they got access to the laptop/server?

**Quality:**
- Do you have 10–20 example inputs with expected results that you rerun after every change to a prompt or a step?
- What is checked by code (format, fields, length), what by a judge model against criteria, and what do you look at yourself on a sample?
- Do you run the same set against the old and new prompt side by side and compare the numbers? That is an A/B experiment for an agent.
- When is a judge model the wrong tool? If regex, a schema, or a test can check the result, code is usually cheaper; high-stakes errors (medicine, law, money) need a safer check; with fewer than 50 cases, a quick human review is faster; and a judge using the same model may praise its own work.

This is a **production readiness checklist**. Save your answers to `my-experiments/u4-readiness.md`.

If you answered "no idea / didn't think about it" to every question — that's not a failure. That's **the time to think about it now**. Better on paper now than at 2 AM in a production incident.

</Phase>
