<Phase type="reflection">

A good agent spec answers these questions **before** any code is written.

Don't picture this as a questionnaire — picture it as an **architectural blueprint**: a building doesn't go up until there's a drawing. A mistake on paper costs a pencil stroke. A mistake in the foundation costs a teardown. The architect holds the entire structure in mind at once — load paths, utilities, fire exits — before a single pile is driven.

| Question | What goes in the answer |
|---|---|
| **Trigger** | What kicks off the agent? (cron / webhook / event / poll / manual run) |
| **Inputs** | What arrives? (format, volume, source) |
| **Steps** | What nodes does the pipeline consist of? |
| **AI vs Code** | Which nodes are LLM, which are code (see u2)? |
| **Outputs** | Where does the result get written? |
| **Failure modes** | What can break, what to do? |
| **Observability** | Where do you look to see what happened? |
| **Cost ceiling** | Max spend per day? |
| **Human-in-loop** | Where is your review needed? |
| **Quality** | How will you check the agent answers well? (a set of examples with expected results) |

If even one question has no answer — the foundation isn't ready to pour. Which load-bearing element in your blueprint is still without support?

</Phase>

<Phase type="concept">

**Agent specification template**

```markdown
# Agent: [name]

## Goal
[One sentence: what the agent does, what pain it solves]

## Trigger
- Type: cron / webhook / event / poll / manual
- Params: [e.g., every 5 minutes / on Gmail label / on repo push]

## Pipeline
1. [Node type] — [what it does] — [in → out]
2. [Node type] — [what it does] — [in → out]
3. ...

## AI nodes
List of nodes where an LLM is used:
- Node X: model [provider/model], prompt in `prompts/x.md`
- ...

## Tools / APIs
- Gmail API (scope: ...)
- Notion API (workspace: ...)
- ...

## Storage
- Where the result is written
- Idempotency: how we avoid duplicates

## Observability
- Trace: the model gateway's log / OTel / stdout logs (Langfuse is an option too; the author removed it because nobody read it)
- Alerting: where errors go (Telegram / email / Slack)

## Failure modes
| Scenario | Behavior |
|---|---|
| LLM 500 | Retry 3× with exp backoff, then fallback model |
| Bad input | Log + Telegram alert + skip |
| Storage full | Hard fail + alert |

## Cost
- LLM calls per day: ~N
- Estimated $: ~$X
- Hard cap: $Y (via provider budgets)

## Human-in-loop
- Where: [step N]
- What you confirm
- How: [Telegram message / Notion task / email]
```

**Real example of a filled-out spec** — a Gmail agent:

```markdown
# Agent: Gmail inbox assistant

## Goal
Every two minutes or so, the agent processes new personal inbox mail, assigns
one of five labels, and prepares a draft when a reply is needed. Sending is
possible only after a human clicks the button.

## Trigger
- Type: poll
- Params: Gmail API about every two minutes, up to 20 emails per pass, oldest first

## Pipeline
1. Poll — fetch new emails — () → [up to 20 emails]
2. Normalize — standardize fields — [email] → [normalized]
3. Classify — choose `AI/Now`, `AI/Later`, `AI/FYI`, `AI/Newsletter`, or `AI/Ignore` — [normalized] → [label]
4. Apply — add the label and archive when required — [label] → [Gmail thread]
5. Draft — write a reply draft when needed — [normalized] → [draft]
6. Review — dashboard: confirm label / approve and send / remove — [draft + label] → [human decision]
7. Send — send in the same thread through Gmail API — [approved draft] → [sent]

## AI nodes
- Classify — LLM through the model gateway, with the five labels and their meanings
- Draft — LLM through the model gateway, writes a draft only

## Tools
- Gmail API: label and archive only; sending is a separate post-button step
- SQLite: `inbox.db`, email states and failure reasons

## Storage
- One Docker container on a server; dashboard access through Cloudflare Access with a PIN
- Idempotency: `new → labeled/drafted → sent/failed`; after five failures, a dead-letter queue

## Observability
- Service log + SQLite email state
- Model gateway log, with usage recorded by service name
- Dashboard metric: “hours since last processed email”; a green container does not prove the flow is alive

## Failure modes
| Scenario | Behavior |
|---|---|
| Gateway 5xx | Retry 3× with a pause; after 5 failures, dead-letter queue |
| Gmail access failure | Stop the pass and wait 15 minutes |
| Stale Gmail cursor | Read the mailbox again instead of jumping straight to “now” |
| Missing gateway key | Refuse to start; do not pretend the inbox is empty |

## Cost
- At most two LLM calls per email; the pass is capped at 20 emails
- Every request carries the service name; usage is visible in the gateway log

## Human-in-loop
- On the dashboard I confirm the label, approve and send, or remove the proposal
- The agent cannot delete mail or send without confirmation
```

This is **on paper**. There's no code yet. But anyone — including me six months from now — can read it and understand what the agent does.

### The clone's other half: the charter

The spec above is the **plumbing**: triggers, nodes, storage. The agent's hands. But if your clone **talks** — answers, co-thinks, holds a dialogue — plumbing isn't enough. It needs a **charter**: who it is, what it believes, what it never does. That's its brain.

The difference is simple: the spec answers "how it runs," the charter answers "who it is when it talks to a human." A prompt without a charter is one-off. A charter turns it into a **stable co-thinking partner**: tomorrow, a month from now, in someone else's hands, it holds the same frame.

The template is seven blocks. Filled once, it lives in the project's `AGENTS.md` or the agent's system prompt:

```markdown
# Agent Charter: [clone name]

## Identity — who it is
One sentence: role + stance. Not "a bot for X," but a co-thinking [role] that [how it holds itself].
> Example: "A co-thinking editor: cuts the excess and protects the author's voice, instead of rewriting for them."

## Profile — what it carries
The context it always holds:
- Domain: [field]
- Who it works with: [audience / yourself]
- What matters about the person: [situation, level, request]

## Principles — what it believes
3–5 working beliefs it decides by:
- [principle 1]
- [principle 2]
- [principle 3]

## Use / Avoid — boundaries
- Call it when: [where it's strong]
- Don't call it when: [where it would harm, or it isn't its role]

## Loop — how it works in one turn
The cycle it repeats every time:
1. [first it clarifies / asks …]
2. [then …]
3. [at the end …]
> One focus per turn. Meaning and the decision stay with the human.

## Laws — hard limits
What must not be broken:
- Never: [prohibition]
- Always: [commitment]

## Goal — why it exists
One sentence: what result the person gets if the agent works well.
```

The seven blocks aren't arbitrary. **Identity + Profile + Goal** give the agent its footing ("who I am, for whom, to what end"). **Principles + Laws** are its character and brakes. **Use/Avoid + Loop** are how it acts in the moment. Drop any one and the agent starts to drift.
