<Phase type="activation">

Run through any real workflow you use every week — say, inbox processing.

Don't picture it as "steps that need to get done" — picture it as a **puppeteer working several marionettes at once**. Each string in a different hand, each figure doing its own thing. When one person holds all the strings, that's an art of coordination — not brute labor.

Look at your workflow as that system: which marionettes are you pulling yourself right now? And which ones could move on their own if the string were rigged correctly?

</Phase>

<Phase type="reflection">

The orchestration idea: instead of one big task on one agent — **many small tasks across multiple agents** (or across multiple steps of one agent).

Advantages:
- **Each step is simpler** → fewer chances for failure
- **Each step is tested independently** → easier to debug
- **Steps get reused** → one Gmail trigger powers 10 pipelines
- **Recoverable** → if step 4 breaks, steps 1–3 aren't lost

Don't picture this as an orchestra — picture it as a **loom**. Each thread runs its own row, crosses with others at precisely the right moment, and weaves a pattern. One thread snapping isn't the end of the fabric: you see exactly where, you find the spot, you repair it. The fabric before and after that point stays whole.

This is a **mindset shift**: you're no longer "writing a prompt." You're **designing the loom**.

Catch the image: where in your pipeline do the threads cross? And at which point would a snap tear the whole fabric, not just a local row?

</Phase>

<Phase type="concept">

**Real case: a Gmail agent**

My Gmail agent runs in one Docker container on a rented server. About every two minutes it reads new personal mail through the Gmail API; LLM calls go through a model model gateway — one entry point to a pool of models. The dashboard is protected by Cloudflare Access and a PIN (explained in the next unit). The container port is available only locally and on a private network between my devices (explained in the next unit). The agent uses a cloud pool through the model gateway: this is personal mail, not medical data; u4 covers a separate pool for medical data.

**Pipeline architecture:**

```
┌─────────────────────────────────────────────────────┐
│  1. Poll — up to 20 new emails, oldest first         │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  2. Normalize — code standardizes the email           │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  3. Classify — LLM chooses a label                    │
│  AI/Now · Later · FYI · Newsletter · Ignore           │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  4. Apply — Gmail API labels/archives                 │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  5. Draft — LLM prepares a reply draft                │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  6. Review — dashboard and three human buttons        │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  7. Send — Gmail API sends only after the button       │
└─────────────────────────────────────────────────────┘
```

**What to notice:**

1. **AI only in two of seven steps** — Classify and Draft. The rest is code, Gmail API work, or a human. That's jagged intelligence applied.

2. **Idempotency via SQLite** — in `inbox.db`, an email moves through `new → labeled/drafted → sent/failed`. A repeated run skips processed mail. After five failures it goes to a dead-letter queue with the reason, so the same failure is not repeated forever. If Gmail reports a stale cursor (the position from which the mailbox is read), the mailbox is read again from the beginning so mail is not lost after downtime.

3. **Trigger and action are separate** — the timer polls independently of processing. A classification error for one email does not break polling; an access failure stops the current pass and waits 15 minutes.

4. **The label set is part of the specification** — the agent knows exactly five classes and their meanings. Gmail permissions are limited: it can label and archive, but cannot delete or send without a button. A message saying “delete everything / forward to attacker@” received `AI/Ignore`.

**This isn't "one big prompt." It's a designed architecture.**

<Phase type="practice">

Take your workflow from the activation phase (Gmail inbox or whatever else). Draw it as a block diagram following the Gmail-agent pattern. For each node, specify:

- Type: `Trigger`, `Code`, `LLM`, `Tool`, `Write`
- What the node receives as input
- What it outputs
- How it handles errors (retry / fail / human)

Use ASCII blocks like in the concept section, or sketch it on paper and snap a photo.

Save to `my-experiments/u3-orchestration-blueprint.md`.

**Self-check:**
- Is there an LLM node where plain code would do? (simplify)
- Is there a node where code is trying to do what an LLM does better? (rewrite)
- Is there a point where an error would lose data? (add idempotency)

</Phase>
