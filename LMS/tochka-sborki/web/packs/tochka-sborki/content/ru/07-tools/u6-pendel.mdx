Уборку обычно откладывают не из лени. Непонятно, с чего начать, а начать со всего сразу страшно: вдруг что-то сломается.

Прикинь в голове: у тебя уже есть агент, который умеет читать весь проект за минуты. Что мешало попросить его просто посмотреть?

</Phase>

## Что такое «Пендель»

**Пендель** — это практика, в которой ты просишь своего агента провести аудит гигиены проекта, а потом чинишь **три** пункта из его отчёта. Ничего устанавливать не нужно: хватает агента, с которым ты уже работаешь, — Claude Code, Codex или любого другого, который читает файлы проекта.

Идея простая: весь курс ты добавлял в проект новое — файл правил, память, hooks, skills. Пендель — первый раз, когда ты смотришь на проект целиком и спрашиваешь: что здесь мешает работать дальше?

## Шесть зон аудита

| Зона | Что ищем | Где связь с курсом |
|------|----------|--------------------|
| 1. Размер файлов и монолиты | Самые длинные файлы проекта; файлы, где смешано несколько обязанностей (роутинг, логика, разметка в одном месте) | Длинный файл — длинный контекст (05/u1) |
| 2. Инлайн-стили и смешанные слои | Стили и скрипты внутри HTML или шаблонов вместо отдельных файлов | Агенту проще править то, что лежит отдельно |
| 3. Мусор в настройках агента | Устаревшие разрешения, дубли, абсолютные пути к чужим папкам, ключи и токены в конфиге | Конфиг MCP и hooks (07/u2, 07/u3) |
| 4. Файл правил агента | CLAUDE.md или AGENTS.md: длина, противоречия, устаревшие инструкции | Ориентир около 200 строк (05/u3) |
| 5. Память между сессиями | Есть ли файл с состоянием проекта: что сделано, что осталось, какие проблемы | Сжатие контекста (05/u4) |
| 6. Hooks | Есть ли хоть одна автоматическая проверка; понятно ли, что делают существующие | Hooks и их безопасность (07/u3) |

Если твой агент не поддерживает какую-то зону (например, hooks), он так и должен сказать в отчёте. Это тоже находка.

## Промпт аудита

Скопируй целиком и отправь агенту в корне своего проекта:

```
Проведи аудит гигиены этого проекта. НИЧЕГО не меняй — только читай и отчитывайся.

Пройди по шести зонам:
1. Размер файлов: покажи 10 самых длинных файлов (путь и число строк) и отметь те,
   где в одном файле смешано несколько обязанностей.
2. Инлайн-стили и скрипты: где стили или код лежат внутри HTML/шаблонов.
3. Настройки агента (например, .claude/settings.json, .claude/settings.local.json,
   .mcp.json, конфиг твоего агента): устаревшие разрешения, дубли, абсолютные пути,
   ключи или токены в открытом виде.
4. Файл правил (CLAUDE.md / AGENTS.md): длина, противоречия, устаревшие инструкции.
5. Память между сессиями: есть ли файл, по которому новая сессия поймёт,
   что сделано и что осталось.
6. Hooks: какие есть, что каждый делает; если нет ни одного — скажи.

Формат ответа — таблица: зона | находка | файл | чем мешает | сколько работы (мало/средне/много).
Если в зоне всё в порядке — так и напиши, не придумывай проблем.
В конце предложи ТРИ пункта, которые дадут больше всего пользы при наименьшем риске,
и объясни выбор.
```

Первая строка важна: аудит и починка — разные шаги. Сначала ты видишь картину, потом решаешь, что трогать.

## Правило: чиним три, не всё

Отчёт может оказаться длинным. Не пытайся закрыть его целиком за один раз:

- **Три пункта** — это то, что ты успеешь проверить своими глазами. Двадцать правок за раз никто не проверяет, их просто принимают на веру.
- **По одному.** Одна починка → проверка → коммит → следующая. Если что-то сломалось, ты знаешь, какая правка виновата.
- **Остальное — в список.** Необработанные находки перенеси в TODO.md (05/u2): они не пропали, они ждут своей очереди.

## Как проверить, что починка ничего не сломала

Перед началом убедись, что проект в git и рабочее дерево чистое:

```
git status
```

Если есть незакоммиченные изменения, сначала закоммить их отдельно. Если проект не в git — `git init` и первый коммит (или хотя бы копия папки).

После каждой починки:

1. `git diff --stat` — какие файлы изменены. Если агент тронул то, о чём ты не просил, — это повод остановиться и спросить почему.
2. `git diff` — прочитай сами изменения. Особенно в конфиге и hooks: hook может запустить любую команду (07/u3).
3. **Запусти проект** тем же способом, что обычно: открой страницу, запусти скрипт, прогони тесты, если они есть. Работает как раньше — коммит. Не работает — `git restore .` возвращает изменённые файлы к последнему коммиту. Новые файлы, которые создал агент, `git status` покажет отдельно: их убирают вручную. После отката можно попросить агента попробовать иначе.

## Пример из отзыва

*Это пересказ отзыва читателя о стороннем стартере для Claude Code, а не наш замер. Цифры — его.*

Сам стартер читатель так и не установил, но, по его словам, «получил пинок» и взялся за свой проект. Итог, по его же рассказу: завёл файл SNAPSHOT.md как память между сессиями, разобрал монолитный index.php (роутер ужался с 1295 до 103 строк), вынес стили из HTML, записал правило в CLAUDE.md, почистил settings.local.json и поставил hook на размер файлов — первый hook в своей жизни.

Заметь: это больше трёх пунктов, и так тоже бывает. Правило «три» — не потолок, а защита от правок, которые никто не проверил.

<Phase type="practice">

1. Закоммить текущее состояние проекта (`git status` должен быть чистым).
2. Отправь агенту промпт аудита из этого юнита.
3. Прочитай отчёт и выбери **три** пункта. Можно взять те, что предложил агент, можно свои.
4. Чини по одному: попроси агента исправить пункт → `git diff --stat` и `git diff` → запусти проект → коммит.
5. Остальные находки перенеси в TODO.md.
