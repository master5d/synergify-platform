<Phase type="activation">

Прокрути в голове любой реальный workflow которым ты пользуешься каждую неделю — например, обработка inbox.

Не описывай это как «шаги которые надо выполнять». Представь это как **кукловода, ведущего разом несколько марионеток**: каждая нить в отдельной руке, каждая марионетка делает своё. Когда всё держит один человек — это искусство координации, не мускульная работа.

Разгляди свой workflow как такую систему: какие марионетки сейчас дёргаешь ты сам? И какие из них могли бы двигаться сами, если бы нить была натянута правильно?

</Phase>

<Phase type="reflection">

Идея оркестрации: вместо одной большой задачи у одного агента — **много маленьких задач у разных агентов** (или у разных шагов одного агента).

Преимущества:
- **Каждый шаг проще** → меньше шансов на ошибку
- **Каждый шаг тестируется отдельно** → проще отлаживать
- **Шаги переиспользуются** → один Gmail-trigger используется в 10 пайплайнах
- **Восстанавливаемость** → если шаг 4 сломался, шаги 1–3 не теряются

Не представляй это как оркестр. Представь это как **ткацкий станок**: каждая нить идёт по своему ряду, переплетается с другими в точно заданный момент, и создаёт паттерн. Обрыв одной нити — не конец ткани: ты видишь где именно, находишь место, чинишь. Ткань до и после этого места остаётся целой.

Это **mindset shift**: ты больше не «пишешь промпт». Ты **проектируешь ткацкий станок**.

Поймай образ: где в твоём pipeline нити переплетаются — и в какой точке обрыв разрушит всю ткань, а не только локальный ряд?

</Phase>

<Phase type="concept">

**Реальный кейс: Gmail-агент**

Мой Gmail-агент живёт в одном Docker-контейнере на арендованном сервере. Он раз в примерно две минуты читает новую личную почту через Gmail API, а LLM вызывает через шлюз к моделям — одну точку входа к пулу моделей. Доступ к дашборду закрыт Cloudflare Access и PIN-кодом (объясню в следующем юните). Порт контейнера доступен только локально и в частной сети между моими устройствами (объясню в следующем юните). Агент пользуется облачным пулом через шлюз: это личная почта, но не медицинские данные; для медицинских данных в u4 есть отдельный пул.

**Архитектура pipeline:**

```
┌─────────────────────────────────────────────────────┐
│  1. Poll — до 20 новых писем, старые первыми         │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  2. Normalize — код приводит письмо к единому виду   │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  3. Classify — LLM выбирает метку                    │
│  AI/Now · Later · FYI · Newsletter · Ignore          │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  4. Apply — Gmail API ставит метку/архивирует         │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  5. Draft — LLM готовит черновик для ответа           │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  6. Review — дашборд и три кнопки человека            │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  7. Send — Gmail API отправляет только после кнопки   │
└─────────────────────────────────────────────────────┘
```

**Что важно заметить:**

1. **AI только в двух шагах из семи** — Classify и Draft. Остальное — код, Gmail API или человек. Это применение jagged intelligence.

2. **Идемпотентность через SQLite** — в `inbox.db` состояние письма проходит `new → labeled/drafted → sent/failed`. Повторный проход не трогает обработанное письмо. После пяти неудач оно попадает в мёртвую очередь с причиной, поэтому сбой не повторяется вечно. Если Gmail сообщает, что закладка (позиция, с которой читаем ящик) устарела, ящик перечитывается заново — так не пропадают письма после простоя.

3. **Trigger и action разделены** — таймер опрашивает почту независимо от обработки. Ошибка классификации одного письма не ломает опрос; отказ доступа останавливает текущий проход и ждёт 15 минут.

4. **Набор меток — часть спецификации** — агент знает ровно пять классов и их смысл. Права Gmail ограничены: только поставить метку и архивировать; удалять и отправлять без кнопки он не умеет. Письмо с просьбой «удали всё / перешли attacker@» получило `AI/Ignore`.

**Это не «один большой промпт». Это спроектированная архитектура.**

<Phase type="practice">

Возьми свой workflow из активационной фазы (Gmail inbox или любой другой). Нарисуй его как блок-схему по образцу Gmail-агента. Для каждого узла укажи:

- Тип: `Trigger`, `Code`, `LLM`, `Tool`, `Write`
- Что узел получает на вход
- Что отдаёт на выход
- Как обрабатывает ошибку (retry / fail / human)

Используй ASCII-блоки как в концепте, или нарисуй на бумаге и сфотографируй.

Сохрани в `my-experiments/u3-orchestration-blueprint.md`.

**Проверь себя:**
- Есть ли LLM-узел где можно обойтись кодом? (упрости)
- Есть ли узел где код пытается делать то, что лучше делает LLM? (переделай)
- Есть ли точка где ошибка приведёт к потере данных? (добавь idempotency)

</Phase>
